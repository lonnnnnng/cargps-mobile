# CarGPS 手机版产品规格

作者：long

最低运行环境：Android 8.1 / API 27

当前验证设备：Pixel_9 模拟器

## 1. 产品定位

手机版用于步行、骑行、驾车或临时测速时随手查看定位与当前行程。项目内的 `gps-core` 统一提供定位质量、速度和统计口径，竖屏界面独立组织信息层级。

## 2. 首屏信息层级

1. 顶部在一行完整显示年月日时分秒，并提供日夜模式切换。
2. 定位健康条同时显示文字状态、卫星使用数与定位精度；状态含义不能只依赖颜色。
3. 瞬时速度是首屏视觉中心，单位始终可见。
4. 当前行程卡片显示记录状态、里程、总时长、移动时长和停车时长。
5. 行程平均、移动平均、最高速度和海拔使用单行四列统计带。
6. 经纬度、样本年龄、PDOP/HDOP/VDOP 和 NMEA 类型在紧凑遥测区常显，不再依赖展开操作。
7. 最近行程以三行摘要展示最近 3 条本地记录，包含开始时间、时长和里程。
8. 底部保留唯一主操作；行程进行中才显示结束按钮，结束必须二次确认。

## 3. 交互与视觉约束

- 全部触控目标不小于 48 dp，主要按钮高度 58 dp。
- `Pixel_9` 竖屏主仪表不滚动，所有实时指标、最近行程和操作必须在系统安全区内一屏完整显示。
- 主速度与当前行程区使用固定紧凑高度，不再吞掉页面剩余空间；释放出的纵向空间用于拉开区块层级，避免上松下挤。
- 系统状态栏和导航栏存在时不遮挡内容或操作；固定高度区块不能因动态数值刷新发生位置跳动。
- 数字使用等宽字体，避免时间、速度和统计刷新时发生布局跳动。
- 夜间使用低眩光深色背景；橙色表达主要操作，绿色表达正常节奏或里程，不以颜色作为唯一状态提示。
- 定位过期时冻结统计并把速度归零；定位丢失时显示 `--`。

## 4. 模块与安装边界

- 手机包名固定为 `com.cargps.mobile`，与车机项目包名不同，可以同时安装。
- 拆分基线暂时保留 `minSdk = 27`；后续提高最低版本时由手机版项目独立决策和验证，不与车机项目同步。
- 首轮安装和视觉验收只使用 `Pixel_9` AVD，不能误装到已连接的 Redmi 真机。
- 活动行程和已结束行程使用 Room 管理的本地 SQLite；进程重建后恢复时必须明确显示“已恢复上次行程”。
- 存储恢复完成前行程按钮保持禁用；落库失败时定位健康区必须显示“行程存储异常”，不能继续静默宣称已保存。
- 出现普通持久化错误或磁盘持续不可写且未确认尾批达到 16 点时，应用必须停止接收新的定位点，保留活动行程、常驻通知和“结束行程”入口，并在通知中显示“等待存储恢复”。尾批成功落库并产生新确认检查点后，定位可以自动恢复；错误窗口和被背压拒绝的点不能继续进入行程累计或已确认数据，Runtime 同时断开上一定位样本和速度平滑基线，恢复首点不得跨故障窗口补算。
- “没有活动行程”和“活动行程数据损坏”是两个不同结果。损坏时必须保留原数据库、禁用开始行程并显示可诊断错误，不能自动清库或静默回到空闲。
- 开始、暂停、继续或结束等行程控制命令等待落库确认时，行程按钮显示“处理中”并禁止重复点击；元数据确认失败后保留上一个已确认行程模式。轨迹点可先更新实时统计，但只有批次事务成功后才进入可恢复的确认检查点。
- 用户只能在可见 Activity 内明确开始行程；活动行程由带常驻通知的定位前台服务继续记录，通知必须提供返回应用和结束行程入口。
- 开始行程前必须具备精确定位且系统 GPS Provider 已开启；Android 13 及以上还必须允许行程通知。首次仅近似授权提供一次应用内精确升级入口，升级被拒且系统不再允许请求时转应用设置；其他首次/永久拒绝、系统定位关闭和通知拒绝分别显示中文原因与对应处理入口，失败时不能循环请求或误显示“正在记录”。API 27 不要求通知运行时权限。
- 普通进程异常退出后，启动型前台服务必须先等待存储恢复，再从最后确认检查点恢复活动模式、暂停累计和已落库轨迹；界面明确显示“已恢复”。
- 整机重启后的当前产品边界已经在 API 27 验证：活动行程数据保留，但系统不会自动拉起手机版 Service、通知或 GPS；用户重新打开应用后恢复并显示“已恢复”。产品不宣称开机自动继续记录；若未来需要该能力，必须单独评审 `BOOT_COMPLETED`、后台位置权限、系统版本限制和应用商店政策。
- 正常批次延迟约 1 秒；异常写失败时内存尾批只保证最多 16 点，不保证时间上限。尾批不属于已确认数据，产品只能承诺恢复到最后确认检查点，不能宣称杀进程、断电或 `force-stop` 零丢点。probe-only 真实 Room 探针已在 API 35/API 27 证明：Checkpoint 提交前杀掉整个进程时，16 个已接受但未提交的点可以全部丢失；这精确界定了进程回收窗口，但不等于物理低存储损失率。
- `v0.3.0` 将 M1-M7 的行程确认、定位前台服务、Room v4、权限状态机、单一事件队列、16 点有界背压、进程恢复和当前热路径 Profile 作为正式交付范围。Pixel_9 / API 35、Android 10 / API 29 和 Android 8.1 / API 27 已完成完整 30 分钟 Home、系统设置、锁屏睡眠和解锁返回回归，API 27 另完成整机重启后的“数据保留、用户打开后恢复”边界验证。受控真实 `SQLiteFullException` 在 API 35/API 27 的存储类各 14/14、Runtime/Room 类各 2/2，当前 `gps-core` instrumentation 合计各 16/16，并确认失败批次整体回滚、活动行程、前 16 点和恢复检查点边界保留；该测试通过限制测试数据库页数实现，仍不等价于物理磁盘 `ENOSPC`。M3 提交前进程回收探针已完成双设备新 PID 恢复和 16 点损失量化；前台 Activity 与 Service 同进程回收后的 Service 独立恢复与用户返回重绑也已在 Pixel_9/API 35 与 API 27 通过。当前热路径 Profile 已在 Pixel_9/API 35 重采集并完成两轮相对冷启动对照，但模拟器 CPU 未锁定且第二轮波动明显，不能外推为真机绝对性能。物理 `ENOSPC`、通知与真实 GPS 停止/恢复、断电和 `force-stop` 零丢点作为已接受残余风险保留；API 27/API 29 最终版本号覆盖升级与真实设备 2 小时长测本次未复验。发布文案不得宣称这些异常环境、开机自动恢复或真机后台记录已经验证。
